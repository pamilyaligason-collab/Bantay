# Lane A audit round 1 (Opus): pass_with_issues

1. [major] (ML-09 invariant) share_set lets an admin downgrade the creator's writer link on a no-login person to read-only. The 0004 carers_admin_update policy blocked this with `not is_person_creator`; 0037 dropped that check. The branch is `if adm and cur.can_write is distinct from cw then update public.carers set can_write = cw` and it has no is_person_creator guard. I proved it on a scratch db (bantay_s12_auditA2, chain 0001..0037, psql exit 0): b1 created no-login 'Probe Dep', so the carers row had can_write = t. Admin a1 called share_set(dep, b1, false, true), which returned 'unchanged', and the row then had can_write = f. In desk/Sharing.tsx this happens when an admin clears the Carer box on a creator's 'C' cell and clicks Save. The dependent is then left with no writer (no dose marking). The rehearsal does not cover this case.
2. [major] (ML-13 regression) The creator guard also blocks the person themself. share_set(p_on=false) refuses whenever is_person_creator(p_person, p_carer) is true, and is_person_creator (0004) does not check whether the person has a login. admin-members/index.ts:100 attaches a login to an existing no-login person, and link_creator's writer row stays. After that, the member cannot stop sharing with the person who created their record: the Stop button on SharingScreen gets 42501 and shows 'You cannot change that.' The 0001 carers_delete policy allowed is_self. This breaks the promise 'you can stop at any time' in privacypolicy.html and ShareSheet (ML-12). The migration comment says the guard is for a no-login person, but the code applies it to everyone. The contract text is literal, so the orchestrator should decide, for example by also requiring `owner is null` (ML-04).
3. [major] (ML-07 privacy) An admin can offer a viewer on the records of a member who has a login, without that member agreeing. The rehearsal asserts this: 'admin may offer a viewer on a member (the carer must accept)'. Once the carer accepts, that third person reads the member's readings, meds and consults, and the member is only told afterwards (share_on). This does not fit the Rev 2 line 'the people you share with', nor ML-07's rule that per-user access needs the owner's approval. The builder disclosed it as an interpretation, but it is a privacy policy decision for Lloyd, not something a lane should settle. It needs an explicit decision, or a check in share_set limiting admin offers to people with no login.
4. [minor] (ML-12 copy) share_set returns 'unchanged' even after it updated can_write on an existing link or offer, so the UI cannot tell the admin what changed. The desk shows 'Saved.' after a downgrade that actually took effect, and Carers.tsx shows 'already linked or has an offer waiting.'
5. [minor] (ML-12 copy) AcceptCard copy: 'Not now' sounds like a delay, but it calls share_accept(false), which deletes the offer for good. Also, '<name> wants to share their health records with you' is shown for offers that an admin or a writer carer made on the person's behalf, so the person did not ask for it. A failed Accept always shows the offline copy, even when the real cause was a refusal or the rate limit.
6. [minor] (ML-12 copy) SharingScreen 'Recent changes' is built from the current viewers only. Removals never appear. Any row with added_by null that is not an admin's is labelled 'You shared with X'. That includes link_creator rows made after 0037, because added_at now defaults to now(). On a claimed record, the creator link would therefore read as 'You shared with <creator>'.
7. [minor] (ML-32 tests) e2e/s12-sharing.auth.spec.ts writes 390x844 shots under S12_SHOTS but never freezes the clock (no page.clock / setFixedTime). The brief requires a frozen clock for shots.
8. [minor] (ML-20 gate) I re-ran e2e/s12-sharing.auth.spec.ts on the lane branch alone: exit 1, all 4 tests failed (heading 'Who can see my records' not found), because F1's App.tsx `sharing` view hook is missing. The builder disclosed this. It must be re-run after F1 merges before sign-off.
9. [minor] (ML-07 privacy) share_candidates() returns the auth user ids of every active member to any active member. family_profiles() deliberately hides those ids. The builder disclosed this; it widens what members can see, slightly.
