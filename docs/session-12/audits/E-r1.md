# Lane E audit round 1 (Opus): pass_with_issues

1. [major] (ML-12 copy) PushPermissionRow.tsx: when the Android permission is 'granted' the row says 'On. Family alerts can reach you when Bantay is closed.' That only checks POST_NOTIFICATIONS. It does not check that register() worked, that push_token_claim saved a token, or that the server has FIREBASE_SERVICE_ACCOUNT_B64. If the APK ships before Lloyd's Firebase/secret steps, or on a phone where registrationError fires (no Play services), a carer is told that lock-screen alerts work when none will arrive. AlertsBanner NATIVE_NOTICE on the same phone also says alerts show only when Bantay is open, so the two lines contradict each other. Show 'On' only after a successful claim (kv flag), otherwise use neutral copy.
2. [minor] (ML-12 copy) On old 2.3.0 shells running the new web (NATIVE.md says old shells keep working on the new web) the push plugin is missing natively. checkPermissions rejects, so KEY_PUSH_PERM is never written and the row shows 'Not on yet.' with a 'Turn on' button that does nothing (startPush fails inside its try/catch). Hide the row or say 'Update the app' when the plugin is not implemented.
3. [minor] (ML-12 copy) docs/FIREBASE.md live check step 2 says the Unwell alert arrives 'within about a minute'. Only the SOS (0031) and readings (0035) triggers call dose-watch {mode:'flush'}; raise_mood_alert does not, so mood_unwell waits for the 15-minute cron. Also the job_runs summary->>'fcmPushed' check only counts cron-run flushes: flush-mode calls (SOS) write no heartbeat, so an SOS check against job_runs would read 0 even when the push worked. docs/NATIVE.md:92, a file this lane edited, still says 'There is no server push on the Android app (D-78)' with no note that 2.4.0 changes it. The builder's ML-12 'stale line updated' is only partly true.
4. [minor] (ML-23 other) flushPush: a lasting FCM auth failure (wrong or revoked service-account key, FCM API disabled, so the token exchange fails, sendFcm returns null and the outcome is 'retry') leaves every row that has an FCM-token carer unmarked for the full 12 h. Those rows are re-offered every 15 min and on every SOS flush, and the web push to the same carers is re-sent each time. There is no attempt marker or retry counter, and the heartbeat stays ok=true with fcmPushed 0, so a fully broken FCM path is invisible in monitoring. If the oauth endpoint hangs, each token costs an 8 s timeout, so about 12 sends use up the 100 s budget and web push for older rows waits until it ages out. Separately, a deterministic 400 (payload bug) prunes every token after 5 sends, a permanent negative from an ambiguous 400 (disclosed in risks; recovery only on the next app open).
5. [minor] (ML-13 regression) dose-watch tokensOf throws 'read' on any push_tokens read error other than a missing table. flushPush then throws before any web push is sent, so a transient error on the new FCM table blocks web push for every row in that run (flush mode returns 500). Before this lane web push did not depend on push_tokens. Treat a token read error as 'no tokens' plus a retry flag instead of failing the whole flush.
6. [minor] (ML-08 tests) push_token_claim's rate limit (pin_try 60/h -> 53400) is in the code, but push_tokens_rehearsal.sql has no assert for it, although the checklist answer cites it as done. Direct REST insert into push_tokens (grant insert to authenticated) also bypasses the claim's rate limit, length checks and pin_try. RLS limits these rows to the caller's own user and the cap trigger keeps 3, so the impact is low.
7. [minor] (ML-06 retention) The prune deletes push_tokens where updated_at < now() - 60 days. A successful send stamps only last_ok_at and never updated_at, so a carer who receives pushes but does not open the app for 60 days loses the token silently. Consider greatest(updated_at, last_ok_at). This matches the PLAN text, but it is a safety trade-off worth a decision.
8. [minor] (ML-33 privacy) In both dose-watch tokensOf and broadcast, an error reading app_roles.disabled is treated as 'nobody disabled' (fail-open), so a disabled account's phone can still get template-only pushes (disclosed in risks).
9. [minor] (ML-37 spec) The brief named shots lock-missed, lock-sos and admin-broadcast. None were produced (no device, Firebase not set up). This is disclosed, but the live device proof is still open and must be done by Lloyd per docs/FIREBASE.md before 2.4.0 is called done.
